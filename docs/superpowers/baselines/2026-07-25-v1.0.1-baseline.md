## Hermes compatibility contract

### Target releases

| Hermes release | Tag | Python range |
|---|---|---|
| 0.19.0 | `v2026.7.20` | `>=3.11,<3.14` |
| 0.18.2 | `v2026.7.7.2` | `>=3.11,<3.14` |

Tagged upstream contracts:

- [Hermes 0.19.0 MemoryProvider](https://github.com/NousResearch/hermes-agent/blob/v2026.7.20/agent/memory_provider.py)
- [Hermes 0.18.2 MemoryProvider](https://github.com/NousResearch/hermes-agent/blob/v2026.7.7.2/agent/memory_provider.py)
- [Hermes memory-provider plugin guide](https://hermes-agent.nousresearch.com/docs/developer-guide/memory-provider-plugin)

Both target releases expose the same relevant memory-provider contract at baseline:

- Required identity and lifecycle: `name`, `is_available()`, `initialize()`
- Recall and synchronization: `prefetch()`, `queue_prefetch()`, `sync_turn()`
- Tools: `get_tool_schemas()`, `handle_tool_call()`
- Session lifecycle: `on_turn_start()`, `on_session_end()`, `on_session_switch()`, `on_pre_compress()`, `shutdown()`
- Integration: `on_memory_write()`, `on_delegation()`, `backup_paths()`
- Setup: `get_config_schema()`, `save_config()`

The current provider does not inherit the real ABC in development tests and lacks verified behavior for several current lifecycle/setup methods.

### Discovery correction

The general Hermes plugin manager can inspect the `hermes_agent.plugins` entry-point group, but memory providers in these releases use a separate single-select discovery path. That path scans bundled providers and `$HERMES_HOME/plugins/<name>/` directories for an `__init__.py` containing a memory provider or `register_memory_provider` call.

Consequently, a general package entry point alone is not a reliable v0.19.0/v0.18.2 memory-provider installation mechanism. The approved design now requires an explicit managed shim at:

```text
$HERMES_HOME/plugins/notion_brain/
```

The shim will import the installed Python package, contain no duplicate implementation, and be managed by `notion-brain hermes install|status|uninstall`.
